## Статический dispatch: значимая находка

- Запущен уже существующий `tools/re/dispatch_lock.py` на бинарнике с проверкой SHA-256. Он декодирует 110002 entries dispatch-table и проверяет точное окончание snapshot `0x33dbc5`; class records и origin дополнительно калибруются на геттерах фары V1=0x40/V2=0x50.
- Для принимающих классов `_V12CmdV1` CID 2109 и `_V12CmdV2` CID 2110 обращение из `SpecialMessageFactory.genLockMsg` ci15273, file `0xde9088`, приводит к одному ci19327 `0xeb1b84`: `mov r0,#0x31; mov r1,#0; bx lr`. Следовательно, для этих двух конкретных классов кандидат lock opcode — **0x31**, а не Ezcan B2. Важно: это пока условное статическое доказательство, что HT реально выбирает один из этих receiver-классов, не установлено.
- `tools/re/model_route.py` отдельно восстанавливает имена и CID: `LorinMessageFactory` 1767, `SpecialMessageFactory` 1745, `V12MessageFactory` 1760, `EzcanFactory` 2473. Проверка привязана к тому же хешу.
- Старый `d219.py` при прямом полном fill падает на ImmutableArray до чтения классов: для работы использовать более свежие `resolve_pool.py`, `model_route.py`, `dispatch_lock.py` из проекта. Ошибочный пробный скрипт удалён, остальные пользовательские файлы не тронуты.

## Уточнение фабрики и bool (статически, без BLE)

- `resolve_pool.py --ref 236093 236039 236040` восстанавливает наследование `V12MessageFactory` → `EucLorinSpecialMessageFactory` → `SpecialMessageFactory` (по Class/Type records). В `V12MessageFactory.initCompact` ci31191 поле receiver `[+0xb]` инициализируется через вызовы по `0x1237094` или `0x1237088`; соответствующие allocation stubs загружают tags `0x0083d108` (CID 2109) и `0x0083e108` (CID 2110). Для выбора ветви также фигурирует строка версии `1.4.24` (pool displacement `0x176cf`); точный критерий пока не утверждается. Так связь V12-фабрики с обоими разрешёнными getters сильнее, но конкретное создание фабрики для HT ещё нужно проследить.
- `bool2Bytes` ci9372 вызывает `bool2Byte` ci9373 и кладёт результат в однобайтовый массив. В ci9373 `tst r0,#8`: при нуле получается tagged Smi 2 → integer 1, иначе 0. SDK Dart 2.19.1 `object.cc` около строк 565–568 явно указывает: бит адреса true = 0, false = 1. Значит аргумент true кодируется байтом `01`, false — `00` (для корректного bool). Это совпадает с Ion `Control.LOCK` payload `31 01` / `31 00`; само соответствие аргумента UI действию и полноценный фрейм ещё требуется проследить.
- В `app/src/main/java/dev/vela/v12/Protocol.kt` lock-builder оставлен, но UI специально disabled; менять это без доказательства маршрута и согласованного аппаратного теста нельзя.

## Маршрут модели: найдено важное звено

- В `LorinMessageFactory.init` ci42797: сначала проверка `isV11Series` ci7831, затем `isV12Series` ci7839 (прямой вызов `0x15878f4 -> 0xb7f728`). При true V12 branch `0x158790c..0x1587934` вызывает allocation stub `0x1588204` ci42813, tags `0x006e0208` → CID 1760 (`V12MessageFactory`) и сохраняет экземпляр в поле `[+0xb]`. Далее `0x15880f8..0x158811c` виртуально запускает его инициализацию.
- `isV12HT` ci8234 сначала вызывает тот же `isV12Series`; следовательно, при истинном HT-predicate и корректной работе предикатов объект классифицируется и как V12. Первая V11-проверка сравнивает то же поле с 6 вместо 7, поэтому соответствующие ветви взаимоисключающие. Это статически подтверждает **условный** путь `LorinMessageFactory.init(HT) → V12MessageFactory → _V12CmdV1/V2 → 0x31`; остаётся показать, что конкретный HT-сеанс действительно создаёт LorinProtocol/LorinMessageFactory и что никакой вышележащий маршрут не заменяет команду.
- Воспроизводимые текстовые свидетельства: `docs/evidence/lock/lorin-init-arm.txt`, `v12-routing-arm.txt`, `dispatch-lock.txt`; имена функций разрешены через `funcs.pkl` и `resolve_pool.py` для того же SHA. Это статический анализ, не наблюдение выполнения.

## Маршрут до LorinProtocol (статическая цепочка)

- `InMotionProtocol.parseProtocolType` ci9622 вызывает `matchesList` ci9623; последний вызывает `startsWith` ci505. Первый список из pool `0xc6ef` содержит `V12` (наряду с V11/V13 и другими). Для входного имени, начинающегося с `V12`, первая ветка возвращает pool ref 230901; `preInit` ci9577 сравнивает результат именно с этим ref.
- В совпавшей ветке `preInit` вызывает stub ci9621 `0xc08d5c`: tags `0x006e7208` → CID 1767 `LorinMessageFactory`; затем stub ci9606 `0xc083e0`: tags `0x00977508` → CID 2423 `LorinProtocol`. Поле `[+0xb]` последнего получает созданную фабрику, а сам protocol сохраняется в `[+3]` `InMotionProtocol`. Соответствует специализации в `InMotionProtocol.lock` ci15271, которая проверяет CID 2423 и вызывает `msgFactory → genLockMsg`.
- Тем самым для официального приложения 8.1.34 **при имени, начинающемся с V12, и HT-модельном предикате** статически замыкается путь до opcode `0x31` и bool `01/00`. Реальное входное имя/поля и отправленные BLE-байты для колеса пользователя по-прежнему не наблюдались; это не доказательство отсутствия дополнительных условий, подписи, иного framing либо firmware-гейта. Evidence: `protocol-type-arm.txt`, `protocol-type-helpers.txt`, `lorin-init-arm.txt`, `v12-routing-arm.txt`, `dispatch-lock.txt`; `resolve_pool.py --pp 0xc6ef`.

## Формирование поля команды: `0x60 0x31`

- Прослежен `genCmd` ci8326 `0xba29d0` (полный дизассемблированный листинг `send-command-arm.txt`). Для integer opcode `0x31`: порог `0x20` требует двух байтов, исходная величина записывается как `00 31`; bool-параметр для write задан false (`genSpecialOne2OneWriteMsg` ci8387 `0xba7354` загружает false из `[sl,#0x78]`), поэтому первый байт получает `0x40`; длина >1 дополнительно выставляет `0x20`, последний байт остаётся `0x31`. Итог **поле команды `60 31`**. Вместе с `bool2Bytes` это даёт содержимое `60 31 01` / `60 31 00` до внешнего обрамления.
- Это совпадает с тем, как Ion трактует `0x60` как command и `31 01/00` как payload. Совпадение только части структуры: внешний flags/length/checksum, транспорт и security-путь официального приложения ещё не сопоставлены побайтово.

## Ограничение старого вывода «игнорирует»

- Текущий `BleController.kt` (ветка `Work.Write`, примерно строки 268–289) делает один `send`, ждёт 200 мс и проверяет settings read-back; если чтение отсутствует **или** не совпадает, UI одинаково сообщает «НЕ подтверждено». Следовательно, сам такой статус не отличает непринятый write от потерянного/запаздывающего read-back. Историческое слово «игнорирует» требует исходного лога/контролируемого воспроизведения; не считать его механизмом отказа. Если в предыдущем эксперименте фактически отдельно наблюдали неизменённое состояние, нужны соответствующие записи.

## Security path: что действительно видно

- `LorinProtocol.buildSecurityConnection` ci39217 непосредственно вызывает `LorinGeneralMessageFactory.genRequestEncryptedKeyMsg` ci8627 (`0x1477514 -> 0xbc46f4`), затем `sendAndGetRsp` с `maxRetryTimes` Smi 2 (=1). Это уже не просто наличие строки: существует отдельный вызываемый путь запроса шифроключа. Но пока не доказано, что он выполняется в HT-сессии, какие последующие операции/ключи используются и обязателен ли он для lock.
- `ProtocolWorker.sendAndGetRsp` ci8206 вызывает `CodecHolder.encode` ci9833 (`0xb96a38 -> 0xc16b60`). Фактический encoder внутри holder и возможное преобразование перед BLE требуют отдельной трассировки. Свидетельства: `protocol-lock-security-arm.txt`, `send-command-arm.txt`, `security-encoder-arm.txt`.

## Преобразование до передачи: обнаружен conditional encrypt

- `CodecHolder.encode` ci9833 вызывает общий `Encoder.encode` ci9578 (unchecked entry `0xc0627c`). При encoder CID 2458 (`LorinEncoder`, проверено через Class records) этот метод проверяет bit `0x08` в значении, извлечённом через message `[+7]` и вложенный объект `[+7]`; при выставленном бите вызывает `Cryptor.encrypt` ci9579. При отсутствии бита Lorin-ветка возвращает сериализованные данные без этого вызова. CID 2459 — `EzcanEncoder`, это отдельный путь. Evidence: `lorin-encode-arm.txt`, `security-encoder-arm.txt`.
- `Cryptor.encrypt` ci9579 при null поле контекста или при несовпадении условия `[context+3][+7] == 0x200` возвращает данные без изменения; при выполнении условия цикл от индекса 4 до конца выполняет XOR с байтами контекста, стартовый индекс определяется через исходный байт по адресу `[data+0xe]`. Это наблюдаемое условное преобразование, не доказательство, что именно lock или конкретное колесо требуют шифрование. Семантику поля, цикл индексов и состояние в действующей HT-сессии ещё нужно проверить. Это важное отличие от простого сравнения payload и потенциальная причина для дальнейшего исследования.

## Флаг шифрования конкретного builder'а и различие с Ion

- Уточнение предыдущего раздела: существование `Cryptor.encrypt` **не означает, что обычный builder lock выставляет бит шифрования**. `genSpecialOne2OneWriteMsg` ci8387 вызывает `genSpecialMany2ManyMsg` ci8289 (`0xba737c -> 0xb9ff54`). Последний вызывает `Util.calFormat` ci8318 с машинными аргументами, дающими `0x10 | 0 | 0 | 6 = 0x16`; преобразование ci8319 сохраняет значение 0x16. Результат через `ByteUtil.toUint8` помещается конструктором `LorinMessage` ci8290 в message `[+7]`, а constructor `ci8291` вычисляет check, но не меняет это поле. `0x16 & 0x08 == 0`, поэтому при отсутствии последующей мутации сообщения Lorin-ветка `Encoder.encode` пропускает `Cryptor.encrypt`. Нужно ещё проверить pre-encode hook и фактический runtime; не утверждать, что security-handshake никогда не требуется.
- Важное расхождение для проверки: Ion строит заголовок `0x14`, тогда как найденный путь builder'а статически даёт format `0x16`. Это **не доказанная причина отказа**: нужны побайтовая трассировка сериализатора, остальных полей и проверка на реальном устройстве. Не исправлять команду вслепую.
- Отдельный статический переключатель `[sl+0x44]+0x181c` влияет не на этот format, а на первоначальное значение вложенного data-поля: false → 4, true → 2 (`0xb9ff70..0xb9ff98`, `0xba00a4`); `initProtocol` ci22861 устанавливает false, две другие функции ci36463/36465 устанавливают true. В какой момент и зачем он переключается в конкретной сессии пока не установлено. Этот параметр нельзя приравнивать к флагу шифрования.
- Свидетельства: `builder-encoder-arm.txt` (ci8387/8289/39367/22861/36463/36465), `builder-constructor-arm.txt` (ci8290/8291), `lorin-format-arm.txt` (ci8318/8322), `format-parity-arm.txt` (ci8319), `lorin-encode-arm.txt` (ci9578/9579). Все адреса — file offsets одного `libapp.so` SHA-256 `92a24d380f129750f4893e92e823b878db531dee5483936b1d66c07d015263f6`. Вычисление — статическое, без запуска приложения и колеса.

## Дополнительная адресация data для V12

- Уточнение: первые 4/2 — значение первого поля объекта data, а не обязательно самостоятельный BLE-пакет. `ProductModel.isLorinEuc` ci8250 содержит проверку `isV12Series` (`0xb9c3d8 -> 0xb7f728`, при true возврат true); `DeviceUtils.getHmicDevice` ci8324 для Lorin EUC возвращает `0x21`. Builder ci8289 при отсутствии явно заданного назначения сначала вызывает именно `getHmicDevice` и при ненулевом результате использует его. Для этой статической ветки строится дополнительное поле назначения `0x21`, рядом с первым полем 4 либо 2 в зависимости от глобального переключателя. Сериализация `toBytes` ci44787 обрабатывает эти два необязательных поля перед массивом команды и аргументом.
- Это усиливает гипотезу, что различается **не только format 0x14/0x16**, но и адресная часть. Однако окончательная последовательность на проводе не установлена: нужно отдельно проверить runtime-поля, длину/checksum, pre-encode hook, transport, возможные преобразования и наблюдаемое поведение. Ни в коем случае не подменять исследование пробной отправкой выведенного пакета.
- Свидетельства: `lorin-euc-arm.txt` (ci8250), `lock-message-path-arm.txt` (ci15272/15273/8323/8324/44787/39367), `builder-encoder-arm.txt` (ci8289/8387); адреса и привязка к SHA указаны в листингах.

## Исторический план до подключения телефона (см. новые результаты ниже)

1. Подключить телефон с Android по USB и разрешить ADB; сначала только перечислить устройство и проверить возможность безопасного read-only сбора. REA ранее вернул пустой список. Не устанавливать Frida и не повторять опасный эксперимент с системным запуском.
2. Если существуют старые логи Ion / работающий экспорт BLE с полноценным payload или независимый сниффер — сравнить фактические адреса, format, длину и checksum официального приложения с Ion и зафиксировать firmware/model. Ранее штатный HCI capture на имеющемся телефоне не содержал payload: наличие ADB само по себе не гарантирует захват.
3. После верификации механизма согласовать с владельцем безопасные условия и отдельно получить разрешение на аппаратный тест; не отправлять произвольные lock/unlock кадры. Диагностировать ответ и read-back раздельно, не объединять timeout и mismatch.
4. Исследование пока не завершено: оставшиеся вопросы — pre-encode hook/транспорт, точный итоговый frame и включение security на устройстве, условия активации глобального переключателя, формат ответа и firmware/состояния, наблюдение реального результата. Не считать разницу `0x14/0x16` доказанной причиной без проверки.

- Дополнительный анализ ранее сохранённого официального logcat обнаружил важный пропущенный шаг **непосредственно перед каждым** наблюдавшимся lock и unlock: write формата `AA AA 13 04` (9 байт), ответ `AA AA 12 13` (24 байта), write `AA AA 13 14` (25 байт), ответ `AA AA 12 04` (9 байт), затем основной `AA AA 16 05 ... 60 31` и его ответ. Между первыми write и lock ~116 мс / ~69 мс. Обе последовательности на этом сеансе побайтно совпадают попарно, но это не доказывает их постоянства между подключениями, необходимости или семантики; данные могли включать идентификаторы/секреты, поэтому сырые байты не публиковать.
- Это сильная гипотеза о подготовительном обмене/авторизации, отсутствующем в текущем Ion, но его назначение и криптография требуют установления и проверки. Не воспроизводить сырые записанные токены и не повторять lock вслепую. Следующий шаг: идентифицировать builder и обработку этих кадров в libapp, определить, требуется ли алгоритм/сессионный контекст, отдельно проверить диагностический лог и состояние колеса.
- Уточнение подготовительного обмена по локальному сравнению сохранённого официального logcat: первый короткий запрос имеет структурный префикс `AA AA 13 04 02 00 00 02`, ответ начинается `AA AA 12 13 02 80 02`; затем запрос начинается `AA AA 13 14 02 00 00 82`, а ответ — `AA AA 12 04 02 80 82 01`. В наблюдённом сеансе все 16 байтов содержимого ответа `response1[7:23]` **точно совпадают** с `request2[8:24]`; то же наблюдалось перед обоими действиями. Сами 16 байтов не публиковать и не захардкоживать. Пока это наблюдаемый echo, а не доказательство криптографии, семантики статуса или универсальности; корректная реализация должна получать данные от текущего колеса и валидировать ответы.
- `IonLockTest` отсутствует во всех доступных буферах logcat PID текущего Ion; сама строка тега присутствует в установленном APK, пакет помечен DEBUGGABLE. Причина подавления/отсутствия логов не установлена. Не утверждать, что реальный write подтверждён, только потому что UI дошёл до несовпадения. Для будущего теста может потребоваться локальная диагностическая запись с ограниченным объёмом и без идентификаторов.

### Статическое подтверждение назначения обмена (ARM64)

- Для установленной сборки восстановлены typed Function records и переходы: `LorinProtocol.buildSecurityConnection` CI 43901 вызывает `LorinGeneralMessageFactory.genRequestEncryptedKeyMsg` CI 7763 (0x9d1948), задающий значение 0x02; затем продолжение CI 7764 вызывает `AesUtil.decryptEcbNoPadding` CI 8450 (0x9f9afc) и `LorinGeneralMessageFactory.genVerifyCryptKeyMsg` CI 7765 (0x9d1b24). Последний вызывает `AesUtil.encryptEcbNoPadding` CI 7766 (0x9d1b98) и строит сообщение с 0x82. `InMotionProtocol.buildSecurityConnection` CI 7762 тоже вызывает CI 7763. Это независимое статическое подтверждение связи цепочки 02/82 с security-соединением.
- Оба вызова AES загружают значение из одного слота `[x26 -> #0x88, #0x31c0]`, но его тип, источник, параметры и возможность сокращения decrypt→encrypt требуют анализа. В одной записи ciphertext ответа буквально равен телу следующего запроса; не делать из этого вывод об отсутствии AES и не считать правилом для других моделей, прошивок и состояний.
- Дизассемблирование `docs/evidence/lock/phone-arm64-security-path.txt` не содержит захваченных значений и идентификаторов. Новый обмен или команда колесу не отправлялись.
- По исходнику `BleController.kt` сообщение UI о несовпадении расположено после возврата `send()` и `SETTINGS` ask. Это подразумевает, что локальный вызов записи не сообщил ошибки, но не доказывает получения команды колесом (особенно для write-no-response), кадр на радио и причинность. Возможный запоздавший ответ на прежний запрос состояния отдельно не исключён.
- Длина наблюдаемого второго security write — 25 байт без учёта возможного экранирования. `BleController` сейчас не запрашивает MTU и отправляет каждый буфер одним GATT write; при стандартном ATT MTU 23 доступно лишь 20 байт данных. Фактический MTU данного соединения и фрагментация официального приложения не установлены; в сохранённом PID logcat нет строк с MTU. При реализации обязательно отдельно выяснить/обработать размер и не считать локально собранный фрейм доказательством успешной передачи.

### Локальная экспериментальная реализация защитного обмена

- В исходники добавлен `LockSecurity.kt`: запрос 0x02, строгая проверка ответа с 16 байтами, формирование 0x82 из байтов текущего ответа и проверка наблюдавшегося ответа `80 82 01`. Это намеренно гипотеза, опирающаяся на 4 runtime-пары и статический путь AES decrypt→encrypt, а не доказанный универсальный протокол. Данные не захардкожены, не журналируются и между операциями не сохраняются.
- `BleController` перед lock запрашивает MTU и отказывается, если он меньше 44; отдельно маршрутизирует адресованные security-ответы до фильтра legacy response, без автоматических повторов отправок. При отсутствии/неверном security-ответе lock не отправляется; после защитного обмена повторно проверяются свежесть и неподвижность. Далее только обычный однократный lock и повторное read-back SETTINGS; security ACK не означает подтверждения состояния.
- Добавлен ограниченный debug-файл `lock-test-diagnostic.txt` в app-scoped external files: только время, статусы и параметры самой lock-команды, без security payload и идентификаторов. Сбрасывается в начале каждой попытки; это запасной путь, поскольку logcat-тег на телефоне ранее не наблюдался.
- Локально `gradlew.bat testDebugUnitTest assembleDebug --offline --console=plain`: BUILD SUCCESSFUL, 34 теста, 0 failed/errors/skipped. Тесты включают синтетические 16 байтов с AA/A5, разбиение ответа, экранирование, неверные ответы и точный запрос. APK SHA-256 `a66aca6a2fee446b3789b94b4ee647b49b4b45055608e786f6f4ecc6033179b1`.
- Владелец согласился на установку этой версии поверх текущей и последующий ручной однократный тест включения на неподвижном колесе. REA вызвал установку с `replace=true` (`ev_6d73c0bfa8ee97c2d0d2ff046ab6528729b32a606abe578a04459b61b7b586e1`); независимые `pm path` и `sha256sum` показали установленный APK с точно тем же SHA. Приложение не удалялось, данные не очищались.

Раздельного эксперимента, изолирующего одну-единственную причину старого отказа, не было: рабочая версия изменила security-последовательность и поведение вокруг MTU.

## Итог: как работает проверенный путь Ion

1. Подключиться к V12 HT, убедиться в неподвижности и свежести телеметрии; обеспечить достаточный MTU.
2. Запросить security-данные кадром `AA AA 13 04 02 00 00 02 17`; дождаться валидного ответа `12 13 02 80 02` с 16 байтами. В проверенных случаях эти байты возвращаются в запросе `13 14 02 00 00 82`. Не использовать записанное значение между сессиями.
3. Дождаться строго наблюдавшегося ответа `12 04 02 80 82 01`; при отсутствии или неверном ответе не отправлять lock. В официальном ARM64 между обоими шагами участвуют AES decrypt/encrypt; наблюдаемое равенство wire bytes подтверждено для этого колеса, но не доказано универсальным.
4. Повторно проверить guard; отправить `AA AA 16 05 02 21 60 31 01 60` для lock или `AA AA 16 05 02 21 60 31 00 61` для unlock один раз. Ответ `AA AA 16 05 21 02 E0 31 00 E1` наблюдался для обоих, но не заменяет проверку состояния.
5. Прочитать SETTINGS: payload byte39, mask `0x20`; установленный бит = locked, сброшенный = unlocked. На этом колесе обе операции совпали с запрошенным состоянием; владелец сообщил, что обе работают.

Примечания: не публиковать сырые официальные logcat и 16-байтовое содержимое; оставлять fallback на официальное приложение. Ещё не установлены общность для других колёс/версий, точная семантика кодов ответа и криптоконтекста, полный набор условий/краевых случаев и единственная причина старого отказа.
